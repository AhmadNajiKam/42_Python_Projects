# Project Governance

## Purpose

42 Python Projects is maintained as a solo maintainer project. Its goal is to provide clear, useful, and educational Python projects for the 42 School curriculum.

This document explains how project decisions are made and how contributors can participate.

## Roles

### Maintainer

The maintainer is currently Ahmad Naji.

The maintainer is responsible for:

* Setting the project direction.
* Reviewing and merging pull requests.
* Deciding which issues and proposals fit the project.
* Protecting the quality, educational value, and consistency of the repository.
* Making the final decision when a discussion does not reach agreement.

Being the final decision maker does not mean being the only person worth listening to. Contributor feedback, review comments, and alternative ideas are important parts of the decision process.

### Contributors

Contributors can report bugs, suggest improvements, improve documentation, add tests, and submit pull requests.

Contributors are expected to explain their reasoning, follow the repository conventions, and participate respectfully in review discussions.

## How Decisions Are Made

Small changes, such as typo fixes or minor documentation improvements, can usually be proposed directly through a pull request.

Larger changes should begin with an issue or design discussion. The proposal should explain:

* The problem being solved.
* The proposed approach.
* Alternatives that were considered.
* Possible disadvantages or compatibility concerns.

The maintainer will consider the discussion, relevant technical evidence, the 42 subject requirements, educational value, simplicity, maintainability, and the long term direction of the repository.

There is no formal voting system. Consensus is preferred, but it is not required. When a decision is needed, the maintainer will make the final call and should explain the reasoning clearly, especially when declining a thoughtful proposal.

A decision can be revisited when new evidence, a better solution, or a meaningful change in project needs becomes available. Changing a previous decision is not considered a failure. It is part of maintaining a healthy project.

## Pull Requests and Review

Changes should be made on a separate branch and submitted through a pull request. Direct commits to `main` are not part of the normal workflow.

All pull requests should follow [`CONTRIBUTING.md`](CONTRIBUTING.md) and [`CONVENTIONS.md`](CONVENTIONS.md). Reviews should focus on correctness, compliance with the relevant 42 subject, readability, testing, documentation, and the scope of the change.

Review comments should be specific, respectful, and focused on improving the project. Contributors should respond to substantive feedback and update their pull request when changes are requested.

The maintainer has final approval authority, but review is intended to be a genuine discussion rather than a formality. Meaningful changes should receive another pair of eyes whenever possible.

## Handling Disagreements

Technical disagreement is welcome when it is supported by clear reasoning or evidence. Participants should address the proposal, not the person presenting it.

If disagreement remains after discussion, the maintainer will make the final decision. The decision should be recorded in the relevant issue or pull request so that future contributors can understand what was decided and why.

## Changing This Policy

Changes to this governance document should be submitted through a pull request. The maintainer will review and approve updates, while considering feedback from contributors and the needs of the project.

If responsibility for the repository is transferred to another maintainer, this document should be updated to identify the new decision-making structure.
